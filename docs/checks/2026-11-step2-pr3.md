# Step 2, PR 3: emulator checks

This page records the checks run on the PR 3 build (the home-screen widget
and the timed pause) on an Android emulator: adding the widget from the
picker, the tap and pause path between the widget and Home, auto-resume with
the emulator's clock moved past the resume time, the widget at font 1.0 and
2.0 at two sizes, TalkBack, and the rotation carry-over from PR 2. It lists
the three defects found, with their screenshots and evidence, their fixes
(PR 3's final fixes), the re-checks on the fixed build, and what stays not
tested until the test phone is connected again.

Every result is labelled **"Tested on emulator beacon-api36, Android 16"** or
**"Not tested"**. Nothing on this page was run on the real phone.

## Observations (not defects)

- **O1. The widget showed ON while a 1-hour pause was saved.** This
  happened after the auto-resume checks (ruling 11), in which the emulator's
  clock was moved forward and then set back by hand.
  - The widget session that started at 17:34:48 by the moved clock
    (16:33:26 real) didn't end after about 45 seconds like every other
    session. JobScheduler showed it "Running for: +16m21s", with its wake
    lock held and its timeout pushed out while Beacon was in front.
  - I ended that session by hand with a debug command,
    `cmd jobscheduler timeout -u 0 dev.beacon 6`. WorkManager then queued
    it again with a minimum delay of 45 min 18 s, that is for 17:35:19 by
    the real clock. That matches the session's start by the moved clock
    (17:34:48) plus WorkManager's 30 s back-off.
  - While that work waited, the widget didn't redraw. A widget tap at
    16:50:12 saved a 1-hour pause (`pause_kind = UNTIL`, until 17:50), but
    the widget kept showing ON
    ([40](step2-pr3/40-o1-widget-not-redrawn.png)): it said alerts were ON
    while they were paused. The queued work couldn't run before 17:35:19,
    so the widget would most likely have said ON for about 45 minutes.
    Alerts and Home read the saved pause, not the widget.
  - Removing the widget at 16:52 and adding it again (a new widget id, so
    a new session) cleared it; the new widget drew the saved pause at once
    ([41](step2-pr3/41-widget-readded-saved-state.png)).
  - Likely cause, not tried: Glance 1.2.0 and WorkManager 2.7.1 time their
    sessions by the wall clock, so setting the clock back left the
    session's times in the future.
  - It is recorded as an observation because it followed two things only a
    test does here: setting the clock back by hand and ending a session
    with a debug command. Whether it should be a defect is for the owner.
    A phone whose clock is set back by hand while the widget is updating
    could see the same; that is Not tested on the phone.
- **O2. The resume alarm may fire up to 45 minutes late** (first checks;
  since the final fixes its window is 10 minutes, check 18). For a 1-hour
  pause, `dumpsys alarm` lists the alarm with `window=+44m59s995ms`: Android
  may deliver an inexact alarm up to 75% of its delay late. In check 7, with
  the clock 1 min 39 s past the resume time, the alarm was still pending
  (`whenElapsed=-20s489ms`, `maxWhenElapsed=+43m18s`). Alerts don't depend on
  it (they check the clock), and the screen-on catch-up cleared the pause.
  So a widget left on a screen that stays on can show PAUSED for up to
  45 minutes after the resume time; spec section 13 already says so.
- **O3. TalkBack says "Beacon" after a double tap on the widget.** The double
  tap clicks Beacon's widget (`ACTION_CLICK` on `glance_view_id_000`) and the
  pause is saved. The refresh then replaces that node, TalkBack's focus moves
  to the launcher's frame around the widget, whose label is the picker name,
  and it says "Beacon" and "Actions available, swipe up or swipe down and
  double-tap to activate." It doesn't announce the new state; touching the
  widget again reads it. This is the launcher's behaviour with a redrawn
  widget.
- **O4. The alarm is allowed to run while idle.** With the battery exemption
  on, `dumpsys alarm` shows `type=RTC_WAKEUP … flags=0x8`; before the
  exemption it showed `flags=0x20`. Both are inexact, with the same window.
  Since the final fixes the alarm is a `setWindow` alarm, not allowed
  while idle: `flags=0x0` (check 18).
- **O5. The widget draws the saved state, not the defaults.** The re-added
  widget appeared PAUSED with the saved resume time from its first frame
  ([41](step2-pr3/41-widget-readded-saved-state.png)).

## How each check was done

- **The stored pause:** the debug build's DataStore file, read with
  `run-as dev.beacon cat files/datastore/beacon_settings.preferences_pb` and
  decoded (`pause_kind`, `pause_until`).
- **The resume alarm:** `dumpsys alarm`, which lists Beacon's
  `RTC_WAKEUP` alarm with the tag `*walarm*:dev.beacon/.widget.ResumeReceiver`,
  its time, its window and when it was set; its history lists each
  `alarm_cancelled`. The delivery in check 8 is from
  `dumpsys activity broadcasts history`.
- **The widget's size:** `dumpsys appwidget --proto`, decoded. Its
  `minWidth` × `maxHeight` is the portrait size and `maxWidth` × `minHeight`
  the landscape size. The text `dumpsys appwidget` on Android 16 doesn't
  print the sizes. The launcher's view tree gave the host view in px
  (2.625 px per dp).
- **What the widget draws:** screenshots, plus Glance's views in the
  launcher's view tree, to see which lines are present and their bounds.
- **Glance's sessions:** `dumpsys jobscheduler` (Active jobs, with "Running
  for") and the `*job*r/dev.beacon/…SystemJobService` wake lock in
  `dumpsys power`. In the re-checks, a new session shows as a new job
  number under "Active jobs", and "Recently completed jobs" gives how long
  ago each Beacon job ended.
- **Whether a catch-up ran (re-checks):** the resume alarm's
  `app_standby` time in `dumpsys alarm`, which moves to the moment the
  alarm was set again.
- **Taps:** `input tap` on the widget; resizing by long-press and dragging a
  handle; removing by long-press and dragging to "Remove" with
  `input motionevent`.
- **The clock (ruling 11):** automatic time off
  (`settings put global auto_time 0`), `adb root`, then
  `date 110917342026.00` and later `date 110919252026.00`. Afterwards the
  clock was set from the host's clock, automatic time turned on and
  `adb unroot` run.
- **Screen off and on:** `input keyevent KEYCODE_SLEEP` and
  `KEYCODE_WAKEUP`, checked with `dumpsys power` (`mWakefulness`).
- **Font and the clock format:** `settings put system font_scale 2.0` and
  `settings put system time_12_24 24`.
- **TalkBack:** as in PR 1 and PR 2. TalkBack's "Log output level" set to
  VERBOSE (TalkBack asks to confirm; this emulator has no personal data),
  focus moved by explore-by-touch through the emulator console
  (`adb emu event mouse`), double taps the same way, and this page quotes
  what TalkBack queued (`Pipeline: execute() … action=SPEAK`). Taps on
  Home's buttons were sent with `input tap`, which reaches the app directly.
- **The light-only alert:** overlay access denied with
  `appops set dev.beacon SYSTEM_ALERT_WINDOW deny`, an SMS from the modem,
  the classifier's debug log (`adb logcat -s Beacon:D`), the `beacon:alert`
  wake lock in `dumpsys power`, and `logcat -b events` for the activity's
  lifecycle. Rotation with `accelerometer_rotation 0` and `user_rotation`.
- **Beacon's grants for these checks:** given with the emulator-only
  commands of PR 2's ruling 12 (`cmd notification allow_listener`,
  `appops set … allow`, `dumpsys deviceidle whitelist +dev.beacon`), since
  the setup card was checked by taps in PR 2. The listener's screen-on
  catch-up needs notification access.
