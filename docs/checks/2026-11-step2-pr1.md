# Step 2, PR 1: emulator checks

This page records the checks run on the PR 1 build (Home, Alert settings and
the 3-second Test alert) on an Android emulator: screenshots at the default
and the largest font size, landscape, right-to-left and a TalkBack pass. It
lists every defect found, with its screenshot, how five of the six were
fixed and re-checked, and what stays not tested until the test phone is
connected again.

Every result is labelled **"Tested on emulator beacon-api36, Android 16"** or
**"Not tested"**. Nothing on this page was run on the real phone.

### Why the Custom value was silent (D4)

TalkBack reads a live region when it receives a content-change event from
it. With TalkBack's own event log on, a step from 15 to 20 min sent TalkBack
one subtree change, from the Duration option whose "N min" sub-line changed
width, and nothing at all from the value. Compose 1.11 reports a node's text
change through a property-change pass that keeps only the verdict of the
last property it compares. A `BasicText` also carries three text-substitution
actions that are rebuilt on every change but compare as unchanged, so when
one of them comes after the text in the node's hash order, the text change
is dropped. On this emulator that was always the case. Changes in size or
place are reported separately, as a subtree change of the live region that
holds the node; that is how the countdown is read. The fix makes every step
such a change. The full evidence is in the implementer's report.

## Observations (not defects)

- **Pausing moves TalkBack focus to the top.** After "Pause all alerts" or
  "Turn alerts back ON", the focused button is replaced, and TalkBack moves
  to "Beacon, Heading". The new state ("PAUSED" or "ON") is not announced;
  it is read when reached.
- **Summary rows are two stops.** On Home's "How alerts look" card, the
  label and the value are read separately ("Flashes for", then "1 minute").
  The test overlay's details rows are read as one ("Speed, Medium, 60 a
  minute").
- **"Change" is read twice.** The per-app button reads "Collapsed, Change
  color for Telegram, Change, Button": the spoken label, then the visible
  text.
- **Stop below the fold at font 2.0.** In portrait at font 2.0 the overlay's
  details card and Stop button are below the first screen
  ([f2-test-overlay-colour](step2-pr1/f2-test-overlay-colour.png)). The
  overlay scrolls ([f2-test-overlay-scrolled](step2-pr1/f2-test-overlay-scrolled.png)),
  the test ends by itself after 3 seconds, and Back also ends it. PR 2's
  alert screen has no countdown card, but should be checked for the same.
- **Tab icons don't line up at font 2.0.** When "Alert settings" wraps to
  two lines, its icon sits higher than Home's
  ([f2-home-on-1](step2-pr1/f2-home-on-1.png)). Nothing is clipped.
- **Forced right-to-left with English text.** Bidi reorders some English
  strings: "1 minute" shows as "minute 1", "10 min" as "min 10", and full
  stops move to the start of the line. This comes from forcing right-to-left
  on English text and goes away with a Hebrew translation.
- **TalkBack speech is longer than the test.** On this emulator's speech
  engine, "3 seconds left, This is how your alerts will look, Test alert"
  takes longer than 3 seconds, so the rest of the queued speech is heard
  after the overlay has closed.

## How each check was done

### Screenshots

- Taken with `adb -s emulator-5554 exec-out screencap -p`, at least 1 second
  after each change.
- The screen was driven with `uiautomator dump` (to find elements) and
  `adb shell input tap` and `input swipe`.
- For the blinking overlay, several shots were taken about 300 ms apart and
  the background pixel was read, to keep one colour phase and one black
  phase.
- Each screenshot was looked at for clipping, overlap, unreadable text,
  words split mid-word and anything under a system bar. Scroll-end
  duplicates and most of the landscape scroll series were left out; the
  kept landscape shots cover each part of each screen.

### Font, rotation, navigation and direction

- Largest font: `settings put system font_scale 2.0`. Android 16 scales large
  text non-linearly, so 36 sp titles grow less than 20 sp body text.
- Landscape: `accelerometer_rotation 0`, then `user_rotation 1` and `3`,
  with 3-button navigation (`cmd overlay enable
  com.android.internal.systemui.navbar.threebutton`). Rotation 1 puts the
  navigation bar on the right and the camera cutout on the left; rotation 3
  the other way round.
- Right-to-left: `settings put global debug.force_rtl 1` alone did not
  change the layout (the configuration keeps `ldltr` until the locale is
  updated). It was applied with the Developer options switch "Force RTL
  layout direction", which updates the locale. Developer options were
  switched on for this and switched off again afterwards.

### TalkBack

TalkBack was switched on with `enabled_accessibility_services` and
`accessibility_enabled`, as the controller set out. What it says was read
from its own log:

1. TalkBack's developer setting "Log output level" was set to VERBOSE
   through its settings screen (TalkBack asks to confirm; this emulator has
   no personal data). It was set back to ERROR afterwards.
2. TalkBack then logs each utterance as it is queued
   (`Pipeline: execute() feedback=… action=SPEAK text="…"`) and again as the
   speech engine speaks it (`SpeechControllerImpl: Speaking fragment`). The
   queued line holds the whole utterance, so it is what this page quotes.
   The "Speaking fragment" lines were used to check what was actually heard
   when the overlay opened.
3. **Moving focus:** shell-injected events (`adb shell input …`, including
   `input keycombination ALT_LEFT DPAD_RIGHT` and fast swipes) don't go
   through TalkBack's touch exploration on this image: they reach the app
   directly as plain taps. So focus was moved with the emulator console,
   which drives the virtual touchscreen like a real finger:
   `adb emu event mouse X Y 0 1` (finger down, a few small moves over
   0.7 s), then `adb emu event mouse X Y 0 0` (finger up). This is
   explore-by-touch: TalkBack focuses the control under the finger and
   speaks it, as it would for a person touching the screen. A TalkBack
   double tap (activate) was two quick down/up pairs through the console.
4. Scrolling used `adb shell input swipe`, which scrolls the app directly.
   `uiautomator dump` was not run while capturing speech, because it pauses
   TalkBack ("TalkBack off" … "TalkBack on").
5. The accessibility tree from `uiautomator dump` was used as a cross-check:
   it shows each control's class (`android.widget.RadioButton`,
   `android.widget.Button` on Compose's role nodes), checkable and checked
   state, selected tab, disabled buttons and content descriptions.

### Re-checks after the fixes

- **Speech:** read the same way as the first TalkBack pass (verbose log,
  explore-by-touch through the emulator console). This TalkBack logs the
  parts of each utterance with full stops ("1 min. Radio button. 2 of 4"),
  and the table above quotes it as logged.
- **Events TalkBack receives (D4):** TalkBack's developer setting "Filter
  accessibility event logging" was set to `TYPE_WINDOW_CONTENT_CHANGED`, so
  TalkBack logs every such event as it arrives (`A11yEventDumper`), with its
  change type and, for the node it reads, whether that node is a live
  region. An app trace (`atrace -a dev.beacon`) showed when Compose ran its
  accessibility checks. Both were set back afterwards.
- **Bar colours (D1) and the chevron (D2):** measured from the full-size
  screenshots, before scaling down, by reading pixel colours.

## Emulator settings changed and restored

After the checks, the emulator was left running with font scale 1.0,
right-to-left off, rotation automatic, gesture navigation, light mode,
Developer options off, TalkBack off and TalkBack's log level back to ERROR.
Two things changed for good: Android Accessibility Suite asked to send
notifications when TalkBack first started, and was answered "Don't allow";
and Beacon's own settings were left as the checks set them.

**During the re-checks** the emulator lost its adb connection. After force
right-to-left was switched off, Developer options were unset with `settings
delete` while their Settings screen was still open in the background. The
Settings app then turned Developer options off its own way, which also
turned USB debugging off, and saved both. It was repaired without wiping the
emulator:

1. In the first seconds of boot, while adb still answers, adbd was restarted
   as root and the Android framework was stopped.
2. In `/data/system/users/0/settings_global.xml`, `adb_enabled` was set back
   to 1 and the `development_settings_enabled` entry was removed (unset, as
   before), using the emulator's own `abx2xml` and `xml2abx`.
   `persist.sys.usb.config` was set to `adb`.
3. The framework was started again, and adbd was returned to non-root.

The emulator was restarted three times on the way, headless, as above.
Three temporary files from the repair are still in the emulator's
`/data/local/tmp` (`g.xml`, `g.abx` and `settings_global.orig`, copies of
its global settings); removing them was blocked by a safety check and is
left to the owner.

After the re-checks: font scale 1.0, right-to-left off, rotation automatic,
gesture navigation, light mode, Developer options unset, USB debugging on,
adbd not root, TalkBack off, TalkBack's log level ERROR and its event log
filter empty. Beacon's settings are as before: Custom 10 min, Medium,
different colour per app (Yellow, Green, Blue), Telegram off.
